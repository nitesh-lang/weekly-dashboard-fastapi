# Weekly Dashboard — monorepo of THREE independent apps

This repo develops, builds and serves three apps on one Render service.
**STRICT RULE: the three must never collide. Every change stays inside its
app's lane. Violating any boundary below is a bug, even if it "works".**

| App | Code lives in | URL space | Data |
|---|---|---|---|
| Weekly Dashboard | `weekly_app/`, `frontend/`, `scripts/`, `data/` | everything EXCEPT /sales* and /buybox* | files in `data/` + Neon mirror (`WEEKLY_DATABASE_URL`) |
| Sales Dashboard | `sales_dash/` (FastAPI) + `sales_dash_frontend/` (SPA) | `/sales`, `/sales-app` | its own Neon (`DATABASE_URL`) |
| Buybox Report | `buybox_src/` (app + pullers + `data/` store) | `/buybox` | committed files under `buybox_src/data/`, encrypted into the bundle at build |

## Boundaries — check before every change

1. **Routes.** Weekly never registers a path starting `/sales` or `/buybox`;
   sales/buybox never register outside their prefixes. Sub-app mounts in
   `weekly_app/main.py` are declared BEFORE the SPA catch-all — keep it so.
2. **Cross-imports are forbidden.** `weekly_app` never imports from
   `sales_dash` (except the guarded mount block in main.py) or `buybox_src`;
   `sales_dash` never imports `weekly_app`. Shared logic = copy, don't couple.
3. **Python namespace.** `sales_dash` ships a package named `app`, reachable
   because `sales_dash/` is APPENDED to sys.path. Never create a top-level
   `app/` module or package in this repo, and never prepend to sys.path.
4. **Env vars.** Before adding/changing one, grep ALL THREE apps for the name.
   Reserved: `DATABASE_URL` + `SP_*` + `SESSION_SAMESITE/SESSION_SECURE` +
   `SYNC_SALES_TOKEN` = sales · `WEEKLY_*` + `COOKIE_SECURE` = weekly ·
   `BUYBOX_*` = buybox build. `SESSION_SECRET` is shared by value on purpose.
   (Render env changes apply at the NEXT DEPLOY, not on restart.)
5. **Cookies.** `weekly_session` (weekly) vs `sales_session` (sales). Never
   rename either to the other or to bare `session`.
6. **Failure isolation.** Both mounts in `weekly_app/main.py` are wrapped in
   try/except so a broken sales/buybox can never stop Weekly from booting.
   Never "clean up" those guards.
7. **Build outputs.** `sales_dash_dist/` and `buybox_dist/` are REGENERATED by
   Render on every deploy — never hand-edit them; committed copies are
   local-dev seeds only. `weekly_app/static/spa/` likewise.
   ⚠ **The AUTHORITATIVE build command is the service's DASHBOARD setting,
   NOT render.yaml** — this service predates Blueprint linkage, so render.yaml
   is documentation only (discovered 2026-08-31 when a BSR upload stayed
   invisible: the yaml's regen/encrypt steps had never run). Change builds via
   Render API/dashboard AND mirror the change into render.yaml for the record.
8. **Crons.** `buybox-daily-bsr` / `buybox-monthly-sync` workflows stage with
   pathspecs scoped to `buybox_src/` — keep it that way so a data cron can
   never commit unrelated working-tree drift. `weekly-sync` must never touch
   `sales_dash*` or `buybox_src`.
9. **Dependencies.** Weekly + sales share the root `requirements.txt`
   (pandas is PINNED 2.2.3 — two production incidents behind that pin; bump
   deliberately, all environments at once). A dependency bump must be checked
   against BOTH apps. `buybox_src/requirements.txt` is CI-only.
10. **Verification.** Any change touching a boundary (main.py mounts,
    auth_guard prefixes, render.yaml build, env) must verify all three after
    deploy: `/health`, `/sales-app/healthz`, `/buybox/` (expect 303 anon).
11. **Nested session middlewares clobber each other.** A mounted sub-app with
    its own SessionMiddleware shares `scope["session"]` with the host's —
    weekly's layer once DELETED the operator's login whenever a sales request
    carried an empty sales session ("login doesn't survive much", fixed by
    `WeeklySessionMiddleware` path-skipping `/sales-app`). Any future mount
    that manages sessions MUST be path-excluded from weekly's session layer.
12. **No heavy work in request handlers.** The web instance is 512MB shared
    by three apps — an in-request snapshot rebuild once OOM-killed it mid-
    upload. Derivations run in the Render build step or GitHub Actions;
    request handlers validate, commit, and return.

Frozen upstream repos (history only, never develop there):
`nitesh-lang/sales-dashboard-multi`, `nitesh-lang/Buybox_report`.
Keepa/BSR data refresh is MANUAL by operator decision — the daily BSR
workflow stays disabled; don't re-enable it or ask for the key.
